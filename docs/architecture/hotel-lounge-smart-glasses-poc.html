Phone → glasses

One display card per detected person

The WebSocket sends a full detection_set snapshot with one profile object per stable face. A separate face_crop message carries the JPEG. The phone joins the messages by crop_id and keeps each card keyed by track_id; guest_id identifies the matched profile. This keeps two people with the same name distinct.

Phone-side display object assembled from both messages

{
  "guest_id": "guest-a81b...",
  "display_name": "ALEX",
  "track_id": "track-a81b...",
  "cropped_face": "<JPEG from crop cache>",
  "preferences": ["Sparkling water"],
  "allergies": ["Peanut allergy"]
}

The image is not repeated in every snapshot. Clients cache crops by crop_id and discard them when the track leaves the set or its five-second TTL expires.

A transient no_match or unconfirmed frame does not clear a previously stable guest or extend its TTL. Full snapshots keep that guest visible until five seconds after the last stable observation; a stable refresh renews the TTL. Guest departure, stream disconnect, and TTL expiry still remove the result.

Before inference, the worker rechecks capture age, rejects duplicate or out-of-order sequence numbers, and favors the newest queued frame. A returned face crop is attached only to a candidate identity supported by that detection.

Enrollment reports a status to the dashboard. Temporary worker outages are retried every five seconds, and active templates are rebuilt from stored reference photos after a worker restart. SQLite holds the reference photos; active embeddings stay in memory, so pgvector is not needed for this small POC cohort.

Clients can opt in with debug_faces: true to receive transient crops for every face returned by the model, including faces below the identity-match threshold. The debug response includes detector scores and worker timings; lounge-control also reports the frame handoff time. Docker logs show the same scores and timing metadata without image bytes.

Optional M1 inference benchmark

The default Docker face-worker uses ONNX Runtime CPU for a portable baseline. On an Apple Silicon laptop, compose.m1-native.yaml keeps lounge-control and mock-hotel in Docker while routing frames to the native macOS worker using Core ML with CPU fallback. The worker health response reports its per-model providers and startup time; enabling COREML_PROFILE_COMPUTE_PLAN=true logs operation placement for Neural Engine/GPU/CPU verification. Use the README benchmark commands to compare identical frame/reference inputs, detection and match counts, p50/p95 latency, throughput, and dropped frames.
