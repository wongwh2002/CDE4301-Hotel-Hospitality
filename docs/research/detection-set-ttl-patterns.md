# TTL and expiry patterns for the lounge detection set

**Checked:** 2026-10-22
**Scope:** Short-lived, per-stream detected-person records in the lounge POC.

## Summary

There is no single TTL algorithm used by every production system. The right choice depends on whether the system needs prompt in-process expiration, shared state across service replicas, or eventual storage cleanup. Redis combines passive expiration on access with incremental active expiry; managed database TTL features such as DynamoDB's are deliberately asynchronous; application timers may use heaps or timing wheels when the number of deadlines makes periodic scans expensive. ([Redis `EXPIRE`](https://redis.io/docs/latest/commands/expire/), [DynamoDB TTL](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html), [Kafka `TimingWheel`](https://github.com/apache/kafka/blob/trunk/server-common/src/main/java/org/apache/kafka/server/util/timer/TimingWheel.java))

For this POC, keep the current per-stream dictionary and prune expired entries while producing the one-second full snapshot. It is simple, and building the full `detection_set` already requires walking every active person. Consider a min-heap only if measurements show that expiry scans—not full-snapshot creation or face inference—are consuming meaningful time. This recommendation follows from the current code path and the workload's one-second full-snapshot contract; it is not a universal industry rule. ([current cache implementation](../../apps/lounge-control/devices.py#L157), [snapshot publisher](../../apps/lounge-control/main.py#L108), [broadcast loop](../../apps/lounge-control/main.py#L121))

## What the POC currently does

- `DETECTION_TTL_SECONDS` defaults to 5 seconds. A stable observation time is converted from UTC `matched_at` to a monotonic-clock `last_seen`; this avoids using wall-clock time for the in-process countdown. ([TTL setting and observation conversion](../../apps/lounge-control/devices.py#L20), [`observation_last_seen`](../../apps/lounge-control/devices.py#L143))
- The cache is a nested in-memory dictionary: stream ID → track ID → person plus `last_seen`. On `get_detected_people`, lounge-control checks each track, removes entries where `now - last_seen >= TTL`, and returns the remaining people. That expiry pass is O(n) in the number of tracks for that stream. ([cache and prune loop](../../apps/lounge-control/devices.py#L157))
- The broadcast loop publishes a full snapshot for every active stream every second by default. Publishing that complete list is itself O(n), because every active person must be included in the message. Other code paths can publish an immediate snapshot after a match update, so the prune can run more often than once per second when those events happen. ([interval](../../apps/lounge-control/main.py#L83), [snapshot publisher and loop](../../apps/lounge-control/main.py#L108))
- Expiration is lazy: there is no per-track timer that fires exactly at the deadline. The entry is removed when the next code path reads/prunes that stream's set. With the periodic loop running, the phone normally sees an expired person disappear in the next full snapshot, up to roughly one broadcast interval later, plus processing and network delay. This follows from the implementation's periodic read-and-publish loop. ([pruning](../../apps/lounge-control/devices.py#L157), [periodic broadcast](../../apps/lounge-control/main.py#L121))

## Patterns used in production systems

| Pattern | How it works | Fit for this detection set |
| --- | --- | --- |
| **Lazy expiry plus periodic cleanup** | Expire an item when it is accessed and found past its deadline; periodically inspect some or all entries to remove expired items nobody reads. Redis documents both passive expiry on access and active incremental sampling of keys with expirations. ([Redis `EXPIRE`](https://redis.io/docs/latest/commands/expire/)) | This is close to the current POC design. A simple full scan is reasonable while each stream has few detected people. The outgoing full snapshot still needs O(n) enumeration. |
| **Min-heap / priority queue** | Store `(deadline, stream_id, track_id, generation)` ordered by earliest deadline. Refreshing a track pushes a new deadline; when an old heap entry reaches the top, discard it if its generation no longer matches the current dictionary entry. This generation check is an implementation technique to make refreshed deadlines safe without searching the heap for the previous entry. Python's `heapq` is a min-heap with the smallest deadline at its root; Kafka's implementation notes priority-queue timers have O(log n) insertion/deletion costs. ([Python `heapq`](https://docs.python.org/3/library/heapq.html), [Kafka `TimingWheel`](https://github.com/apache/kafka/blob/trunk/server-common/src/main/java/org/apache/kafka/server/util/timer/TimingWheel.java)) | A practical next step if there are many tracks and expired-item cleanup is measured as costly. Due cleanup is proportional to the number of deadlines popped, but the full snapshot remains O(n). Repeated refreshes can leave obsolete entries in the heap until their deadlines pass, so track heap growth or periodically rebuild it. |
| **Timing wheel** | Bucket deadlines by time tick; each tick processes one bucket. Kafka describes its hierarchical timing wheel and says its timer has O(1) insertion/deletion costs versus O(log n) for priority-queue timers. The trade-off is bucket/tick-based scheduling and more data-structure complexity. ([Kafka `TimingWheel`](https://github.com/apache/kafka/blob/trunk/server-common/src/main/java/org/apache/kafka/server/util/timer/TimingWheel.java), [Netty `HashedWheelTimer`](https://netty.io/3.5/api/org/jboss/netty/util/HashedWheelTimer.html)) | Appropriate only if the service has very many concurrent deadlines and can tolerate tick-level expiry granularity. A one-second snapshot cadence already makes sub-second cleanup unlikely to improve what the phone sees. |
| **Redis key TTL** | Redis deletes expired keys passively when accessed and actively via background sampling. Expiry notifications are emitted when Redis deletes a key, not guaranteed exactly when its TTL reaches zero; Pub/Sub is fire-and-forget. ([Redis `EXPIRE`](https://redis.io/docs/latest/commands/expire/), [Redis keyspace notifications](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/)) | Useful later if lounge-control replicas need shared active state or state must outlive a process. Do not depend on expiry notifications to remove a person from the phone promptly; build outgoing snapshots from records whose explicit deadline is still in the future. |
| **Database-managed TTL** | Storage services can delete expired records asynchronously. DynamoDB says expired items are typically deleted within a few days and recommends filtering expired items from reads while deletion is pending. Cassandra treats expired TTL data as tombstones and removes tombstones through compaction. ([DynamoDB TTL](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html), [DynamoDB filtering](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ttl-expired-items.html), [Cassandra tombstones](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/tombstones.html)) | This is storage cleanup, not a real-time five-second client-presence mechanism. It is not a reason to add a database to the POC detection set. |

## Expiry and notification are separate requirements

The TTL deadline answers, “Is this record still valid?” The cleanup mechanism answers, “When do we reclaim it from memory or storage?” The notification mechanism answers, “When does the phone learn that it is gone?” These can happen at different times. Redis explicitly warns that an expired event may be delayed until deletion, and DynamoDB documents that expired-but-not-deleted items can remain visible to reads unless filtered. ([Redis keyspace notification timing](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/), [DynamoDB expired-item reads](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ttl-expired-items.html))

In this POC, a record becomes logically expired at `last_seen + 5s`; the one-second full snapshot is what normally communicates its removal to the phone. If the product later requires removal at the deadline with less than one-second scheduling delay, add a deadline scheduler and publish a new full snapshot when that track expires. Keep the periodic full snapshot as a resynchronization path for reconnects and missed WebSocket messages. The current code publishes periodic complete snapshots and prunes during snapshot construction. ([current cache implementation](../../apps/lounge-control/devices.py#L157), [snapshot loop](../../apps/lounge-control/main.py#L121))

## Recommendation and scale triggers

1. **Keep the current scan for the POC.** The expected per-stream set is small, and complete snapshots must enumerate all active people regardless of how expiration is indexed. The current scan is straightforward to inspect and test. ([current cache implementation](../../apps/lounge-control/devices.py#L157), [snapshot publisher](../../apps/lounge-control/main.py#L108))
2. **Measure before replacing it.** Record active tracks per stream, number of streams, prune duration, full snapshot serialization/send duration, event-loop lag, and how late an expired person disappears from a phone snapshot. These are proposed project measurements, not requirements stated by the cited systems.
3. **Try a min-heap if pruning becomes material.** A practical project trigger is p95 prune time above 100 ms (10% of the one-second snapshot interval), or evidence that pruning delays the snapshot loop. Treat 100 ms as an initial local guardrail to validate against the target laptop and expected number of phones, not an industry standard.
4. **Consider Redis only for a state-sharing requirement.** Examples include multiple lounge-control replicas needing a shared detection cache, or recovery after a process restart. Even then, filter by the explicit expiry deadline before sending a snapshot because managed TTL cleanup and notifications are not exact at the deadline. ([Redis expiry behavior](https://redis.io/docs/latest/commands/expire/), [Redis notification timing](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/))
5. **Consider a timing wheel only at much higher timer volume.** Its insertion/deletion advantage matters when scheduling huge numbers of deadlines; for one-second full-set messages over a small lounge cohort, it would add moving parts without removing the O(n) work of preparing each complete message. ([Kafka `TimingWheel`](https://github.com/apache/kafka/blob/trunk/server-common/src/main/java/org/apache/kafka/server/util/timer/TimingWheel.java))
