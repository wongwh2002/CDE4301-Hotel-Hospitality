# Smart-glasses camera and SCRFD feasibility

**Research date:** 2026-10-10
**Scope:** Whether InsightFace SCRFD-10GF can run on the project's Rokid Glasses RV101 or Meta glasses, and how detection results could reach the local `lounge-control` service. This assesses documented SDK paths, not measured performance.

## Short answe

- **Meta:** the supported camera path is an iOS/Android companion app using the Wearables Device Access Toolkit (DAT). DAT exposes video frames to that app, so running SCRFD in the Android phone app with ONNX Runtime is technically plausible. Meta does not document a supported custom SCRFD runtime on ordinary Ray-Ban/Oakley glasses. Meta Ray-Ban Display Web Apps run on the glasses, but the current public Web App FAQ lists display/input/context capabilities, not a camera-frame API.
- **Rokid RV101:** Rokid documents both a phone-side CXR-L integration and an on-glasses CXR-S SDK path. CXR-S is the promising direct-on-glasses research route because Rokid says it can build standalone apps and access the camera. I found no vendor documentation establishing ONNX Runtime/SCRFD support or sustained inference performance on RV101. The public CXR-L camera example I could verify is a still-photo callback (`takePhoto`); continuous live frame delivery remains unproven for this exact device and SDK path.
- **Recommended POC:** keep inference in the existing laptop Docker `face-worker`. Have the companion phone obtain camera data and use the project’s device WebSocket to send sampled frames to `lounge-control`; it can forward them to `face-worker` over the existing internal HTTP contract. Test phone-side ORT only as a later optimization, and on-glasses inference only after a CXR-S spike.

## What the model does—and does not do

SCRFD-10GF is the face **detector** in InsightFace's `buffalo_l` pack. It reports face boxes and five keypoints; it does not tell the system which guest it sees. Identity matching also needs a face-alignment/recognition model (the pack's ResNet-50 recognizer), active guest templates, and a comparison policy. A Boolean `face_detected` HTTP event can wake a service or record that a face is present, but cannot identify that person. [InsightFace model-zoo table](https://github.com/deepinsight/insightface/blob/master/python-package/docs/model_zoo.md) · [InsightFace SCRFD implementation](https://github.com/deepinsight/insightface/blob/master/python-package/insightface/model_zoo/scrfd.py)

The `10GF` label is a compute tier, not a 10 GB model: InsightFace reports about 9.98 GFLOPs and 3.86 million parameters for SCRFD-10GF at VGA resolution. Its listed 4.9 ms inference result is from a Ryzen 9 3950X CPU, so it does not predict performance on a phone or glasses. [SCRFD model table and benchmark setup](https://github.com/deepinsight/insightface/blob/master/detection/scrfd/README.md)

## Is ONNX Runtime available on the phone?

Yes. ONNX Runtime publishes an Android package for Java/Kotlin apps, and its NNAPI execution provider can use Android CPU/GPU/neural accelerators on supported Android versions. This makes SCRFD ONNX inference on a companion phone a reasonable prototype, but the InsightFace Python `FaceAnalysis` wrapper does not become an Android app automatically. The app still needs compatible preprocessing, SCRFD output decoding/NMS, face alignment, and—if it must identify a guest—the recognition model and cosine matching. NNAPI placement and latency vary by phone/model operators, so compare CPU first and measure NNAPI on the target phone. [ONNX Runtime mobile development](https://onnxruntime.ai/docs/tutorials/mobile/) · [ONNX Runtime Android build/package](https://onnxruntime.ai/docs/build/android.html) · [ONNX Runtime NNAPI provider](https://onnxruntime.ai/docs/execution-providers/NNAPI-ExecutionProvider.html)

## Recommended data path and staged plan

1. **Use the existing POC path first:** glasses → vendor SDK on paired phone → authenticated device WebSocket to laptop `lounge-control` → internal HTTP handoff to Docker `face-worker` → match callback/cue over the same device session. This matches the current proposed architecture and preserves one local inference implementation. [Current architecture proposal](../architecture/hotel-lounge-smart-glasses-poc.md)
2. **RV101 gate:** with the exact glasses, phone, firmware and CXR-L version, prove whether the app can receive repeated timestamped frames at a useful cadence and return a cue to the display. Until then, use one-shot capture/replay only for interface wiring; do not claim continuous recognition is demonstrated. If CXR-L does not provide a stream, ask Rokid for a supported CXR-S/CXR-L streaming path before designing around it.
3. **Meta mobile comparison:** use a supported Ray-Ban Meta or Oakley Meta device and DAT Android sample to measure the actual frame format, cadence, permissions, reconnects and capture-to-laptop delay. The sample's 30 FPS maximum is a selectable API setting, not a guaranteed sustained rate.
4. **Edge-inference experiment:** after camera delivery works, compare (a) laptop Docker inference and (b) Android phone ORT inference with SCRFD-10GF. Measure detector latency p50/p95, sustained frame throughput, dropped/stale frames, phone temperature/battery and face recall across realistic sizes/distances. If the phone only detects, send a crop/frame onward for laptop identity matching; to keep images local, port recognition/alignment too and provision the active guest templates securely to the phone.
5. **On-glasses experiment only after vendor confirmation:** for RV101 CXR-S, confirm custom app entitlement, camera/frame API, model-file support, supported inference runtime/accelerator, memory headroom and thermal limits. Do not build this path using Glass3 SDK docs.

## HTTP versus WebSocke

An Android companion app can make normal HTTP requests to the laptop's LAN address. For this POC, the existing device path is one authenticated WebSocket per phone for frames and cue traffic; `lounge-control` uses internal HTTP calls to `face-worker`. The implemented WebSocket accepts frame metadata, frame bytes, and ping messages. It does **not** currently accept a phone-submitted match/detection result, so phone-side inference would require a new authenticated message type or HTTP endpoint and a contract that validates the device session and active candidate before showing any cue. Send image bytes only when the laptop still needs them for identity matching. Never send only a face-present boolean and treat it as a guest identity. [Current device WebSocket implementation](../../apps/lounge-control/main.py) · [Current architecture interfaces](../architecture/hotel-lounge-smart-glasses-poc.md)

## Key uncertainty

The largest blocker is RV101 camera delivery, not the existence of an ONNX runtime. Rokid publicly documents standalone CXR-S apps and CXR-L photo I/O, but public docs do not settle whether the exact RV101/CXR-L SDK supports continuous frames, nor whether an RV101 app can sustain SCRFD-10GF. Meta DAT provides a clearer phone-side frame API, though real-world sustained rate and on-phone SCRFD performance still require measurement.
