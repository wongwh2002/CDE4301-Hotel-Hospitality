# Face CV models: current landscape for the lounge POC

**Research date:** 2026-10-10
**Scope:** Face detection and face-embedding models relevant to the local, CPU-first Docker POC. “SOTA” depends on the task, benchmark, image quality, and compute budget; there is no single best model for all of them.

## Short answe

Yes. YuNet + SFace was the small, convenient baseline; the current face-worker implementation now uses InsightFace `buffalo_l`. For detection, SCRFD offers a range of accuracy/compute choices. For embeddings, larger ArcFace-family systems such as `buffalo_l` report strong results on harder benchmarks; AdaFace is specifically designed to account for varying image quality. Recent 2026 research is also adapting CLIP ViT-L/14 for face recognition, but this is a research-scale direction rather than a light laptop replacement.

For this project, use `buffalo_l` as the accuracy-oriented POC model. The current replay still uses the same synthetic portrait for enrollment and query; it validates pipeline wiring, not recognition accuracy.

### Detection notes

OpenCV describes YuNet as lightweight and compatible with OpenCV DNN. Its model page still cites 2023-era WIDER Face AP values of 0.834/0.824/0.708, while the same page’s newer evaluation table lists 0.8844/0.8656/0.7503. Treat these as indicative, not a direct head-to-head with another repository’s results; use one evaluation script and input protocol when comparing. The `2026may` YuNet file is described as a dynamic-shape re-export of the 2023 model, not a new accuracy model, and is documented for OpenCV 5.x’s ONNX Runtime engine. The POC currently pins OpenCV 4.x, so it is not a drop-in upgrade. [OpenCV Zoo YuNet notes and results](https://github.com/opencv/opencv_zoo/blob/main/models/face_detection_yunet/README.md)

SCRFD’s paper and official repository report a strong efficiency/accuracy range, including a small 500M model and more compute-heavy 10GF/34GF versions. The paper’s headline speedups are GPU results; the repository’s 28.3 ms CPU figure is for a specific AMD CPU and PyTorch setup, so benchmark the exported ONNX model in our container before choosing it. [SCRFD paper](https://arxiv.org/abs/2105.04714) · [SCRFD official benchmark table](https://github.com/deepinsight/insightface/blob/master/detection/scrfd/README.md)

### Recognition notes

SFace is a MobileFaceNet-based embedding model and has an efficient OpenCV path. Its public benchmark scores are useful baselines, but LFW is near saturation and should not stand in for small, blurry, profile, or video faces. AdaFace changes training margins according to image quality and reports gains on IJB-B, IJB-C, IJB-S, and TinyFace; it is worth testing if phone/glasses frames are often low quality, but it is not a guaranteed drop-in win without a matching detector, preprocessing, and local test set. [SFace model description](https://github.com/opencv/opencv_zoo/blob/main/models/face_recognition_sface/README.md) · [AdaFace CVPR paper](https://openaccess.thecvf.com/content/CVPR2022/papers/Kim_AdaFace_Quality_Adaptive_Margin_for_Face_Recognition_CVPR_2022_paper.pdf)

The latest notable research direction I found is the accepted IJCB 2026 AFMFR competition: teams adapted CLIP ViT-L/14 using synthetic identity data, with full fine-tuning plus Sub-Center ArcFace winning the full-data track and rank-stabilized LoRA leading the limited-data track. It covers LFW through IJB-C and TinyFace, but involves adaptation/training and a much larger foundation-model backbone; it is not a practical small CPU-first Docker swap for this POC. [IJCB-AFMFR 2026 paper](https://arxiv.org/abs/2607.24422)

For an edge/mobile recognizer, **FaceLiVTv2** is a newer candidate worth tracking: its April 2026 paper reports an accuracy/latency improvement over earlier lightweight models on mobile and CPU benchmarks. Its published inference example uses PyTorch, so it would need an integration/export check before it fits this worker's InsightFace/ONNX Runtime path; the paper's reported benchmark gains should also be reproduced on our camera frames. [FaceLiVTv2 paper](https://arxiv.org/abs/2604.09127) · [authors' code and inference example](https://github.com/novendrastywn/FaceLiVT)

## How the current `buffalo_l` pipeline works

`buffalo_l` is a **model pack**, not one end-to-end network: InsightFace lists SCRFD-10GF for face detection, ResNet-50 trained on WebFace600K for recognition, plus 2D-106/3D-68 alignment and age/gender models. This worker passes `allowed_modules=["detection", "recognition"]`, so it loads only the first two tasks. Its CPU ONNX Runtime provider is selected explicitly. [InsightFace model-zoo table](https://github.com/deepinsight/insightface/blob/master/python-package/docs/model_zoo.md) · [worker implementation](../../apps/face-worker/vision.py)

The flow is: **frame → SCRFD face boxes, scores, and five landmarks → landmark-aligned 112×112 face crop → 512-value embedding → normalized cosine comparisons**. InsightFace's recognizer code aligns the image from the five detector keypoints, runs its ONNX recognition network, and provides cosine similarity; the worker takes `normed_embedding`, normalizes it again, and compares it to each active candidate template. A cosine score is a similarity measure, not a probability that an identity is correct. The pack's 2D-106/3D-68 models are separate alignment modules; they are not enabled in this worker. [InsightFace recognition implementation](https://github.com/deepinsight/insightface/blob/master/python-package/insightface/model_zoo/arcface_onnx.py) · [face analysis flow](https://github.com/deepinsight/insightface/blob/master/python-package/insightface/app/face_analysis.py) · [InsightFace feature fields and dimensions](https://github.com/deepinsight/insightface/blob/master/python-package/docs/person_analysis.md)

InsightFace returns independent face observations for a frame; it does not provide temporal tracking. This repository adds IoU box association across frames, active-cohort cosine matching, a provisional threshold and runner-up margin, three consecutive stable observations, and timeout/clear behavior. Those are application policies around the model, not model outputs. [InsightFace API scope](https://github.com/deepinsight/insightface/blob/master/python-package/docs/person_analysis.md) · [face-worker matching logic](../../apps/face-worker/worker.py)

## Staged selection plan

1. **Build a clean local set.** Use consented, representative captures with multiple sessions per person and separate identities/sessions between threshold calibration and holdout evaluation. Include known lounge candidates and unknown people; vary distance, pose, lighting, motion blur, occlusion, and phone compression. Keep the current same-image replay only as a pipeline smoke test.
2. **Measure recognition and detection separately.** For each candidate, report face miss/no-face rate and known-person false reject / unknown false accept rates. Calibrate its own cosine threshold and best-versus-next margin on calibration data, then freeze them before holdout scoring. Do not reuse `0.65` as a universal threshold.
3. **Compare the cheapest controlled alternatives first.** Run `buffalo_l` versus `buffalo_m` to isolate detector cost because recognition weights match; then try `buffalo_sc`/`buffalo_s` if bundle size or CPU cost remains too high. Only then integrate `antelopev2`, AdaFace, or FaceLiVTv2 with their own detector/alignment path and matching thresholds.
4. **Benchmark the actual deployment shape.** On the same Python 3.14 CPU container and laptop, measure model cold start and warm per-frame p50/p95 detection+embedding latency, sustained throughput, queue drops, CPU/RAM, and model-cache size with one and two simultaneous phone streams. Separate camera/network/cue latency from inference. A benchmark using another CPU, GPU, framework, or image protocol does not predict this result.
5. **Choose from the measured error/latency trade-off.** Keep `buffalo_l` if it meets the locally set false-match/false-reject target and frame budget. Prefer `buffalo_m` if detection is the bottleneck and recognition quality holds; step down to `buffalo_sc`/`buffalo_s` only if their holdout error rates remain acceptable. Keep a larger or newer recognizer only if it improves the target failure cases enough to justify integration and runtime cost.

## Benchmarks and limitations

- WIDER FACE is useful for detecting faces across scale, pose, and occlusion, but its validation scenes do not reproduce a glasses camera’s field of view, motion blur, image compression, wearer angle, or hotel lighting. Published scores also vary with test scale, threshold, and evaluation implementation. The project needs a small, representative, consented capture set.
- LFW and similar verification accuracy scores are not the same as this system’s open-set 1:N task: one frame is matched against a changing active-lounge cohort, with an “unknown” outcome required. Tune thresholds and the best-versus-next margin on that task; scores from different papers cannot set our production threshold.
- NIST’s ongoing FRTE publishes 1:1 verification and 1:N identification evaluations, including accuracy and resource measures. It is a useful external reference for deployed recognition performance, but its submitted algorithms are not a plug-in model catalogue. [NIST FRTE 1:1](https://pages.nist.gov/frvt/html/frvt11.html) · [NIST FRTE 1:N](https://pages.nist.gov/frvt/html/frvt1N.html)

## Recommendation for this repo

1. **Use InsightFace `buffalo_l` for the POC now.** It combines SCRFD-10GF detection with a ResNet-50 ArcFace embedding model and is the strongest straightforward package identified in this comparison. The package's larger footprint and CPU cost are accepted for the accuracy-first prototype.
2. **Keep `buffalo_m` as a later speed comparison.** InsightFace reports the same recognition benchmark scores for `buffalo_m` and `buffalo_l`; `buffalo_m` uses the smaller SCRFD-2.5GF detector. Compare both if `buffalo_l` cannot keep up with the phone frame rate.
3. **Use a realistic evaluation before trusting matches or changing thresholds.** Include multiple consenting people and unknown guests; vary distance, head pose, lighting, blur, glasses, and phone compression. Report false matches, missed matches, no-detection rate, and p50/p95 latency separately. Keep the synthetic identical-image replay only as a smoke test.

These recommendations are for the laptop-on-LAN POC. They do not establish an accuracy, privacy, or deployment-readiness claim for the Rokid camera path or real hotel guests.
